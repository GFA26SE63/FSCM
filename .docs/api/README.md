# API contract rules

The FSCM API is the authoritative boundary for the approved [business baseline](../business/README.md). OpenAPI is the canonical REST contract. This document defines rules that every feature contract must follow; it does not invent endpoint paths that have not been reviewed.

## Contract principles

- Expose task-oriented commands and stable resource queries, not persistence entities.
- Enforce role and assignment scope on every request.
- Revalidate mutable business inputs on the server; client totals and availability are estimates.
- Make state-changing mobile operations idempotent.
- Use optimistic concurrency on mutable aggregates and inventory balances.
- Return machine-readable business errors with enough context for the client to recover.
- Preserve historical snapshots in responses for settled transactions.
- Publish breaking changes through explicit contract versioning, never silent field reinterpretation.

## Authentication and authorization

Authentication identifies the user. Authorization combines the user's role with current scope:

| Role | Required scope examples |
| --- | --- |
| Sales | Assigned sales group/territory and retailer |
| Warehouse Keeper | Assigned warehouse |
| Sales Manager | Managed regions/groups |
| Retailer | Own retailer account and orders |
| Operator/Admin | Explicit permission for the requested transition |

A list response must be filtered to authorized rows, and a direct identifier lookup must independently enforce the same scope. Clients must not infer authorization from hidden buttons or cached assignments.

## Request metadata

State-changing requests should carry:

| Value | Purpose |
| --- | --- |
| Access token | Authentication and claims |
| Correlation ID | End-to-end diagnostics; generated by the API when absent |
| Idempotency key | Deduplicates supported commands |
| Expected version/ETag | Detects stale aggregate updates |
| Device-created time | Informational offline timestamp; never FCFS authority |

Never place secrets, tokens, or personal evidence in URLs or logs.

## Idempotency

Idempotency is mandatory for offline order sync, receipt confirmation, payment confirmation, loyalty earning, and reward redemption. It is also recommended for approval, cancellation, dispatch, and transfer receipt commands.

The key is scoped to the authenticated actor and operation. The server stores a request fingerprint and final outcome:

- Same key and same fingerprint: return the original result.
- Same key and different fingerprint: return an idempotency conflict.
- In-progress key: return a retryable/in-progress result without starting duplicate work.
- Expired key: handle according to the documented retention window; do not silently duplicate a settled business transaction.

## Concurrency

Commands that mutate a versioned resource include its expected version or `If-Match` value. A stale command returns a conflict and the current version; it does not overwrite newer state.

Inventory conflicts trigger a bounded server-side retry only when the whole allocation can be safely recomputed. Exhausted retries return a retriable conflict. Clients must not retry with altered business values under the same idempotency key.

## Error model

Use Problem Details-compatible responses with a stable FSCM error code:

```json
{
  "type": "urn:fscm:error:inventory-insufficient",
  "title": "Order cannot be fully allocated",
  "status": 422,
  "code": "ORDER_INSUFFICIENT_INVENTORY",
  "detail": "At least one order line cannot be fully supplied.",
  "correlationId": "...",
  "errors": [
    { "field": "lines[0].quantity", "code": "INSUFFICIENT_AVAILABLE" }
  ]
}
```

Recommended status semantics:

| Status | Meaning |
| --- | --- |
| 400 | Malformed syntax or contract shape |
| 401 | Missing/invalid authentication |
| 403 | Authenticated but outside role or assignment scope |
| 404 | Resource unavailable within authorized scope |
| 409 | State, version, duplicate-key, or idempotency conflict |
| 422 | Well-formed command rejected by a business rule |
| 429 | Rate or bounded-processing limit |
| 500/503 | Unexpected or temporary server failure |

Do not use success responses for rejected business commands.

## Data conventions

- IDs used by APIs are UUIDs; immutable business display codes are separate fields.
- Quantities are whole cartons in approved order and transfer flows. Reject fractional or negative values.
- VND amounts use integer minor-unit semantics and never binary floating point.
- Percentages and ratios use documented decimal precision.
- Instants use ISO 8601 UTC (`Z`). Clients display Asia/Ho_Chi_Minh time.
- Expiry dates use `YYYY-MM-DD` when time-of-day is not a business input.
- Enumerations are documented strings. Unknown response values must not crash clients.
- Optional, absent, and explicit `null` values must have distinct documented semantics.

## Pagination and filtering

Collection endpoints use deterministic ordering and bounded page sizes. Cursor pagination is preferred for status histories, audit logs, notifications, and sync results; page/size may be used for stable master-data searches.

Filters must reflect business scope, including warehouse, region, sales group, retailer, SKU, batch expiry state, order state, and date range where relevant. The server always applies authorization scope in addition to client filters.

## Offline order contract

An offline submission includes a stable client order key, temporary `OFF-*` code, device-created time, retailer, requested delivery data, lines, and client estimates. The server records `server_received_at`, which is the only FCFS timestamp.

The response returns one authoritative outcome:

- accepted with the assigned `DH-*` code and server snapshots;
- final business rejection with codes and reasons;
- already processed with the original result;
- retryable technical/concurrency failure.

The server revalidates territory access, retailer state, products, quantities, price, promotions, inventory, ETA, MLOR, and configuration. It reports price/promotion differences explicitly. A client never converts an offline draft into an accepted order locally.

## State-transition commands

Approval, rejection, cancellation, picking confirmation, dispatch, delivery, receipt confirmation, payment, complaint review, transfer dispatch/receipt, and reward fulfillment are explicit commands. Each command defines:

- allowed source states and resulting state;
- authorized roles and assignment scope;
- required reason/evidence fields;
- expected aggregate version;
- idempotency behavior;
- stock, payment, or point side effects;
- audit and notification events.

Generic update endpoints must not bypass these transitions.

## Order and allocation responses

Settled order responses expose snapshot values rather than joining current master data for historical display. Allocation explanations may include warehouse, batch, allocated quantity, ETA, remaining life at arrival, score components, sequence, and configuration version. Internal lock/retry details and unauthorized inventory are never exposed.

## Attachments

The API authorizes attachment metadata and issues controlled upload/download access. Validate size, media type, checksum, ownership, and attachment purpose. Store object keys rather than public URLs; evidence access follows the parent order, complaint, or operational document scope.

## Notifications and real-time updates

SignalR or push notifications announce that state changed; they are not the source of truth. Payloads carry stable identifiers and minimal non-sensitive context. Clients re-query the canonical resource after reconnecting or receiving an event.

## Contract lifecycle

1. Record the approved business rule and acceptance examples.
2. Design command/query contracts without persistence leakage.
3. Review OpenAPI changes with backend, web, and mobile owners.
4. Add contract and authorization tests.
5. Update generated/manual clients deterministically.
6. Publish breaking changes through an agreed version and migration window.

Do not document or generate endpoints for pending regional-to-regional rebalancing until it becomes approved scope.
