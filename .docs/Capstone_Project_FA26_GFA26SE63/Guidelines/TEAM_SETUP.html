    FSCM Team Handover: Completed Work and Local Setup

    This document records the FSCM work that has already been completed and gives the team the information needed to continue development. It covers the repository layout, local configuration and run commands, prototype-to-component progress, active GitHub CI, active GitHub-to-Azure DevOps mirroring, and the working backend CD pipeline to Azure App Service.

    Never commit passwords, tokens, connection strings, API keys, .env, local appsettings files, or mobile environment JSON files.

    Completed work summary

    Area Status Work completed
    Repository structure Done Backend, frontend, and mobile are maintained as independent Git repositories, with cross-system documentation in the outer repository.
    Local configuration Done Safe example templates and ignored local settings locations are defined for all three applications.
    Frontend prototype conversion Done for the current prototype scope The React prototype has been organized into reusable UI primitives, shared business components, role-aware navigation, feature screens, typed models, and interactive demo state.
    Mobile prototype conversion Done for the current prototype scope The Flutter prototype has been organized into reusable core/shared widgets and separate Sales, Retailer, and Warehouse feature slices.

    1. Workspace and repository map

    The workspace contains four separate Git repositories. The three application folders are independent repositories; they are not Git submodules of the outer documentation repository.

    Local folder Purpose GitHub repository Azure DevOps repository
    FSCM/ Cross-system README, documentation, and diagrams None currently configured FSCM
    FSCM/FSCM-Backend/ .NET API, tests, GitHub CI, and Azure CD definition GFA26SE63/FSCM-Backend FSCM-Backend
    FSCM/FSCM-Frontend/ React management portal GFA26SE63/FSCM-Frontend FSCM-Frontend
    FSCM/FSCM-Mobile/ Flutter mobile application GFA26SE63/FSCM-Mobile FSCM-Mobile

    The normal remotes inside each application repository are:

    • origin: GitHub; this is the normal development and pull-request remote.
    • azure: the matching Azure DevOps repository; GitHub Actions normally updates it automatically.

    Always run Git commands from the repository that owns the change. For example:

    git -C FSCM-Backend status
      git -C FSCM-Frontend status
      git -C FSCM-Mobile status

    The outer repository ignores all three application folders. Therefore, committing at FSCM/ does not commit application changes.

    3. Local configuration files

    Backend appsettings

    Put local backend settings here:

    FSCM-Backend/src/FSCM.API/appsettings.Local.json

    Create it from the committed example once:

    Copy-Item FSCM-Backend/src/FSCM.API/appsettings.example.json FSCM-Backend/src/FSCM.API/appsettings.Local.json

    Update the copied file with your local PostgreSQL connection, JWT secret, allowed frontend origins, and OpenAI key if that integration is used. The important sections are:

    • ConnectionStrings:DefaultConnection
    • Jwt
    • Cors:AllowedOrigins
    • OpenAI
    • Serilog

    The API also supports environment-specific local files such as appsettings.Development.Local.json. Local appsettings files are ignored by Git.

    Frontend environment

    Put frontend environment values here:

    FSCM-Frontend/.env

    Create it from the committed example once:

    Copy-Item FSCM-Frontend/.env.example FSCM-Frontend/.env

    Supported variables:

    VITE_API_BASE_URL=https://localhost:7027
      VITE_GRAPHQL_ENDPOINT=https://localhost:7027/graphql

    The .env file is ignored by Git. All VITE_* values are bundled into browser code and are public, so never put a secret in them.

    Mobile appsettings

    Put mobile environment values here:

    FSCM-Mobile/env/appsettings.json

    Create it from the committed example once:

    Copy-Item FSCM-Mobile/env/development.example.json FSCM-Mobile/env/appsettings.json

    Expected structure:

    {
        "API_BASE_URL": "https://localhost:7027",
        "GRAPHQL_ENDPOINT": "https://localhost:7027/graphql"
      }

    Files matching FSCM-Mobile/env/*.json are ignored, except committed *.example.json templates.

    localhost on a phone or emulator means that device, not the development computer. Use an address that the device can reach. Android Emulator commonly uses 10.0.2.2 for the host computer. HTTPS requires the device to trust the development certificate.

    4. Run the applications locally

    Run each application in a separate terminal. The commands below start from the outer FSCM/ folder.

    Run the backend

    Before the first run, start PostgreSQL, create the configured database, and ensure appsettings.Local.json contains a valid connection string.

    Set-Location FSCM-Backend
      dotnet restore FSCM.slnx
      dotnet run --project src/FSCM.API/FSCM.API.csproj --launch-profile https

    Local endpoints:

    • HTTPS API: https://localhost:7027
    • HTTP API: http://localhost:5246
    • Swagger: https://localhost:7027/swagger
    • GraphQL: https://localhost:7027/graphql
    • Health check: https://localhost:7027/health

    If the local HTTPS certificate is not trusted:

    dotnet dev-certs https --trust

    Run the frontend

    Set-Location FSCM-Frontend
      npm ci
      npm run dev

    Vite normally serves the portal at http://localhost:5173. That origin must be present in the backend CORS configuration.

    Useful frontend commands:

    npm run lint
      npm run build
      npm run preview

    Run the mobile application

    Set-Location FSCM-Mobile
      flutter pub get
      flutter devices
      flutter run --dart-define-from-file=env/appsettings.json

    Select a particular target when more than one device is available:

    flutter run -d <device-id> --dart-define-from-file=env/appsettings.json

    Values can also be supplied without a file:

    flutter run --dart-define=API_BASE_URL=https://localhost:7027 --dart-define=GRAPHQL_ENDPOINT=https://localhost:7027/graphql

    Useful mobile validation commands:

    dart format --output=none --set-exit-if-changed lib test
      flutter analyze
      flutter test

    7. Completed: GitHub-to-Azure DevOps mirror

    Status: configured and active. Every application repository contains .github/workflows/mirror-to-azure.yml. On every GitHub branch push, the workflow pushes the same branch and full branch history to the matching Azure DevOps repository. It can also be started manually from the GitHub Actions page.

    The completed mirror setup includes:

    • A mirror workflow in each of the backend, frontend, and mobile GitHub repositories.
    • A target URL pointing to the matching repository in the Azure DevOps FSCM project.
    • Full-history checkout so the pushed branch keeps its Git history.
    • A GitHub Actions repository secret named AZURE_DEVOPS_PAT for authenticated Azure DevOps pushes.
    • Automatic mirroring for every branch push and a manual workflow_dispatch option.

    The active branch flow is:

    Developer push to GitHub
              |
              +--> GitHub CI validates the pushed commit
              |
              `--> Mirror workflow pushes that branch to Azure DevOps

    GitHub CI and the mirror are separate workflows and run independently. The mirror is not blocked by GitHub CI. For the backend main branch, Azure Pipelines performs its own build and test stages before deployment.

    Treat GitHub as the source of truth for application code. Avoid direct commits or force-pushes in the Azure mirror repositories. A branch that has unrelated Azure-only commits can reject the next mirror push as a non-fast-forward update.

    Ongoing maintenance is limited to renewing AZURE_DEVOPS_PAT before it expires and updating the secret in all three GitHub repositories. Never put the PAT directly in a workflow or commit it to Git.

    8. Completed: Backend CD to Azure App Service

    Status: configured and active. The backend has an Azure deployment pipeline connected to the mirrored FSCM-Backend repository. Frontend and mobile deployment pipelines are not part of the current completed delivery scope.

    Pipeline definition:

    FSCM-Backend/.azure/pipelines/application-delivery.yaml

    Current pipeline values are stored in .azure/pipelines/variables/backend.yaml:

    Setting Current value
    Trigger branch main
    .NET SDK 10.0.x
    Build configuration Release
    API project src/FSCM.API/FSCM.API.csproj
    Artifact fscm-backend-api
    Azure service connection sc-fscm-dev
    App Service type webApp
    App Service name app-fmcg-api-dev
    Azure DevOps environment backend-production

    The stages are:

    1. Build: restore and compile the solution.
    2. Test: execute the test projects and collect XPlat code coverage.
    3. Package: publish the API and create fscm-backend-api.zip.
    4. Deploy: download the artifact and use ZIP deployment to publish it to Azure App Service.

    The Azure Pipeline triggers when main reaches the mirrored FSCM-Backend Azure repository. Deployment also has an explicit main-branch condition.

    Azure delivery configuration already in place

    • Azure Pipeline YAML: .azure/pipelines/application-delivery.yaml in the backend repository.
    • Azure Resource Manager service connection: sc-fscm-dev.
    • Deployment target: Azure App Service app-fmcg-api-dev.
    • Azure DevOps deployment environment: backend-production.
    • Deployment method: packaged ZIP deployment through AzureWebApp@1.
    • Runtime secrets and environment-specific values are kept in Azure App Service → Configuration / Environment variables, not in Git.

    Typical App Service settings use ASP.NET Core's double-underscore nesting syntax:

    ASPNETCORE_ENVIRONMENT=Production
      ConnectionStrings__DefaultConnection=<production PostgreSQL connection string>
      Jwt__Issuer=<issuer>
      Jwt__Audience=<audience>
      Jwt__Secret=<long random secret>
      Jwt__Algorithm=HS256
      Jwt__AccessTokenExpiryMinutes=60
      Jwt__RefreshTokenExpiryDays=30
      Cors__AllowedOrigins__0=<deployed frontend origin>
      OpenAI__ApiKey=<key, only when required>
      OpenAI__Model=<model name>
      OpenAI__BaseUrl=https://api.openai.com/v1/

    The current Azure resource names contain dev, while the Azure DevOps environment is named backend-production. These are the names already configured in the repository. Change .azure/pipelines/variables/backend.yaml only if the team introduces different development, staging, or production resources.

    End-to-end backend delivery flow

    Push backend commit to GitHub main
              |
              +--> Backend GitHub CI
              |
              `--> GitHub mirror workflow
                       |
                       `--> Azure Repo: FSCM-Backend/main
                                |
                                `--> Azure Pipeline
                                         Build -> Test -> Package -> Deploy
                                                                    |
                                                                    `--> Azure App Service

    9. Common problems

    • Mirror says AZURE_DEVOPS_PAT secret is missing: add or renew that exact GitHub Actions repository secret.
    • Mirror receives a non-fast-forward rejection: check for direct commits in Azure DevOps. Preserve any needed work, reconcile it in GitHub, and restore a single source of truth.
    • Frontend cannot call the API: verify .env, confirm the API is running, and add the frontend origin to backend CORS.
    • Mobile cannot call localhost: use a host address reachable from the emulator/device and handle development certificate trust.
    • Backend cannot connect to PostgreSQL: verify the database service, database name, credentials, port, and ConnectionStrings:DefaultConnection.
    • App Service starts but API configuration fails: verify Azure App Service environment variable names and values, especially the database and JWT settings.
    • A commit appears in the wrong repository: check git rev-parse --show-toplevel before staging files.
    Standalone HTML copy of TEAM_SETUP.md. Keep both files together so the source link continues to work.
